The important idea is that the RAG system shouldn't retrieve Base64. It should retrieve a semantic description of the image.

For example, suppose page 14 contains a photograph of flooding around a roadway.

CODB Docs could produce:

{
  "id": "image_page14_2",
  "type": "image",
  "page": 14,

  "bbox": [82, 214, 510, 480],

  "caption": "Photograph showing roadway flooding",

  "description":
    "Street-level photograph showing standing water covering approximately half of the roadway near a residential intersection.",

  "objects": [
    "road",
    "standing water",
    "vehicle",
    "houses",
    "storm drain"
  ],

  "ocr": [
    "FLOOD ZONE",
    "Atlantic Ave"
  ],

  "context": {
    "heading": "Existing Drainage Conditions",
    "before": "Current drainage deficiencies are shown below.",
    "after": "Proposed improvements will increase stormwater capacity."
  }
}

Now your text-only model can understand the image because it receives:

Page 14 contains a street-level photograph showing standing water covering approximately half of a roadway near a residential intersection...

That's vastly better than feeding it:

/9j/4AAQSkZJRgABAQEASABIAAD...
But I would go further

The surrounding PDF content should participate in understanding the image.

Suppose the image itself is ambiguous:

[image of construction equipment]

A generic vision model might produce:

"Excavator at a construction site."

But CODB Docs knows the image appears under:

Proposed Lift Station Improvements

and immediately below:

Figure 4. Replacement of existing 12-inch force main.

Now you can construct:

IMAGE PIXELS
     +
OCR INSIDE IMAGE
     +
IMAGE CAPTION
     +
NEAREST HEADING
     +
TEXT ABOVE
     +
TEXT BELOW
     +
PAGE CLASSIFICATION
     +
DOCUMENT TYPE
     ↓
Image Understanding

That could produce a much better representation:

Construction photograph associated with the proposed lift station improvements and replacement of the existing 12-inch force main.

That contextual fusion is worth building.

Keep Base64, but don't index it

I'd absolutely allow:

image.base64

because it's convenient for sending the original image to:

your own endpoint

But your RAG index should contain:

image.semantic

rather than:

image.base64

Something like:

{
  id,
  page,
  bbox,

  // binary representation
  blob,
  base64,

  // intelligence
  type,
  caption,
  description,
  ocr,
  objects,
  entities,

  // document context
  heading,
  nearbyText,

  fingerprint,

const results = await doc.search(

For a completely text-only AI

This is where your architecture becomes particularly useful.

You can effectively give a text-only model "vision" through preprocessing:

                  CODB DOCS
                     │
        ┌────────────┴─────────────┐
        │                          │
      TEXT                       VISUAL
        │                          │
        │                    ┌─────┴─────┐

        │                    │           │
        │                  Vision      Analysis
        │                    │           │

                       ▼

                       │
                       ▼
              Everything becomes
               semantic information
                       │

The LLM doesn't need to see pixels.

CODB Docs becomes its document perception layer.

That's a much more interesting direction than merely storing Base64. Base64 should be the escape hatch for sending pixels to a vision system; CODB-IR should store what those pixels mean.
