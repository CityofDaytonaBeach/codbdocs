2. Your model-free query engine works, but has a correctness problem

query.js is explicitly designed as:

"Spatial + semantic search ... using pure heuristics."

That's exactly consistent with your no-model design.

But the current pattern matching is too broad.

For example:

{
  patterns: [
    /organization|company|department|agency|city/i
  ],
  entityType: EntityTypes.ORGANIZATION
}

and:

{
  patterns: [
    /address|location|where|street|avenue|city|zip/i
  ],
  entityType: EntityTypes.ADDRESS
}

Both contain:

city

Because organization comes first, a question like:

What city is the project located in?

can be interpreted as:

ORGANIZATION

instead of:

ADDRESS/LOCATION

That's a real query-routing bug.

You need scoring rather than:

firstRegexThatMatchesWins()

For example:

detectIntent(question)

should collect candidates:

[
  {
    intent: "location",
    score: 0.94
  },
  {
    intent: "organization",
    score: 0.21
  }
]

Then choose the highest score.

3. how much currently returns every currency value

This is a bigger issue for document Q&A.

Question:

How much was the contract?

matches:

EntityTypes.CURRENCY

Then:

const results =
  contentGraph.getEntities(
    EntityTypes.CURRENCY
  );

That retrieves every monetary value in the entire PDF.

If the document contains:

Original contract: $1,000,000
Change order: $250,000
Revised contract: $1,250,000
Budget: $3,000,000
Grant: $500,000

CODB answers with all five.

It needs to preserve the subject:

contract

and rank currency entities according to their relationship/proximity to that concept.

You want:

QUERY
"How much was the contract?"
       │
       ├─ intent = value_lookup
       ├─ expected = CURRENCY
       └─ subject = contract
                    │
                    ▼
          find contract context
                    │
                    ▼
          nearby currency entities
                    │
                    ▼
               rank evidence

That's a major next improvement.

4. The automatic total can produce a misleading answer

Current currency handling does:

const total =
  amounts.reduce(
    (s, a) => s + (a.value || 0),
    0
  );

and then reports:

Total: $...

That's dangerous.

A document might contain:

Original contract      $1M
Change order           $250K
Revised contract       $1.25M

CODB could report:

Total: $2.5M

which is mathematically correct and semantically ridiculous.

Only calculate a total when query intent actually asks:

total
sum
combined
aggregate
all together

And preferably understand relationships before summing.

5. who has the same problem

Question:

Who approved the contract?

currently maps:

who → PERSON

then returns every detected person.

It needs:

{
  intent: "relationship_lookup",

  subject: "contract",

  relation: "approvedBy",

  expectedEntity: "person"
}

Then traverse/rank relationships.

This is precisely where your Document Graph can outperform plain keyword matching.

6. Summary handling looks suspicious

executeQuery() returns:

{
  type: "summary",
  results:
    contentGraph.getSummary()
}

Then executeAsk() immediately does:

if (results.length === 0)

But a summary normally looks like an object, not an array.

If getSummary() returns an object, then:

results.length

is undefined.

It won't necessarily crash, but it's an API-type inconsistency.

Handle summary before array assumptions:

if (type === "summary") {
  return {
    answer:
      formatSummaryAnswer(results),

    confidence: 0.85,
    evidence: []
  };
}

if (!results?.length) {
   ...
}

The engine doesn't need another twenty clever detectors right now. The retrieval layer needs to become contextual.

Replace:

with:

Question
   ↓
Query Parser
   │
   ├─ intent
   ├─ subject
   ├─ expected entity
   ├─ relationship
   ├─ operators

        ↓

   │
   ├─ exact
   ├─ lexical
   ├─ entity
   ├─ fuzzy

   ├─ spatial

        ↓
Relationship Ranking
        ↓

        ↓

        ↓

For:

you ultimately want the parser to produce:

That's the piece that would move your model-free document intelligence from impressive extraction into genuinely sophisticated retrieval.

What's still remaining
Headless Accessible View is still missing. There is still no accessible.js or access/ module and therefore no graph.createAccessibleView(). This is the layer that should build semantic accessible content while leaving UI/design entirely to the consuming React/Lovable/JS app.
query.js has not been updated. Its SHA remains c4c6ed..., so the query problems identified previously remain: overlapping intent regexes, subject context not being preserved, who effectively targeting people too broadly, and how much targeting currency too broadly.
Relationship-aware retrieval still needs completion. The desired flow should be:
"Who approved the $425,000 contract?"
        ↓
intent: relationship_lookup
subject: contract
anchor: $425,000
relation: approvedBy
expected: PERSON
        ↓
Document Graph
        ↓
best matching relationship
        ↓
answer + page + bbox + evidence

rather than simply finding every PERSON entity.

Currency aggregation needs query awareness. CODB should only perform SUM when the question actually requests a total, sum, combined amount, aggregate, etc. Otherwise original amount + change order + revised amount can produce a beautifully precise but completely wrong total.
A proper query planner is still missing. I'd want:
graph.planQuery(question)

producing something like:

{
  intent: "value_lookup",
  subject: ["contract"],
  expected: ["currency"],
  anchors: [],
  relations: [],
  operation: null
}

Then retrieval operates from that plan.

Deterministic operators remain worth adding: SUM, COUNT, AVG, MIN, MAX, COMPARE, BEFORE, AFTER, BETWEEN, and GROUP BY. These are especially valuable because your model-free engine can execute them deterministically instead of asking an LLM to perform interpretive arithmetic.
Concept Graph remains a major intelligence upgrade. You want relationships such as:
contract ↔ agreement ↔ award
vendor ↔ contractor ↔ supplier
SOF ↔ Sufficiency of Funds
cost ↔ amount ↔ value
approve ↔ authorize ↔ adopt

with document-derived aliases and terminology added automatically.

+ structure
+ spatial
+ relationships
        ↓
adaptive ranking
