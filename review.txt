Quite a few. PDF is less a document format and more a box containing 30 years of questionable decisions. If you're building CODB Docs as a document-intelligence engine, these are exactly the failures worth targeting because many tools successfully "open" a PDF while extracting the wrong meaning.

High-value PDF failures to detect
Failure	What commonly happens	What CODB Docs should detect/do
Wrong reading order	Multi-column text gets mixed together	Reconstruct order spatially and structurally
Text exists but is invisible	Hidden OCR/text layer is extracted instead of visible content	Compare rendered page against text layer
Bad OCR layer	PDF has searchable text, but it's garbage	Score native-text quality and automatically re-OCR
Duplicate OCR text	Visible text + hidden OCR produces duplicates	Spatially deduplicate overlapping text
Scanned pages mixed with native pages	Some pages work, others silently return nothing	Detect extraction quality per page
Rotated scans	OCR produces nonsense	Detect orientation and normalize before OCR
Skewed scans	OCR accuracy collapses	Deskew automatically
Text encoded as glyphs	Viewer shows words, extraction gives garbage	Glyph/font mapping + visual/OCR fallback
Missing ToUnicode map	Copy/paste produces nonsense	Detect invalid Unicode mappings
Outlined text	Letters are vector paths, not text	Detect text-like vector geometry + OCR
Flattened forms	Form looks completed but fields no longer exist	Visually recover labels/values
Checkboxes/radio buttons	Extraction misses selected state	Detect marks spatially
Signatures	Signature image gets ignored	Detect signature regions and associate them with nearby labels
Tables without structure	Extractor returns a pile of words	Reconstruct rows/columns/cells geometrically
Tables across pages	Each page becomes an unrelated table	Recognize continuation and merge logical table
Merged cells	Column relationships get destroyed	Infer spanning cells geometrically
Charts	Text extracted but actual values/trends lost	Chart-specific visual analysis
Diagrams	Labels survive, relationships disappear	Build nodes + connectors + spatial relationships
Maps/site plans	OCR gets street names but loses geographic meaning	Preserve labels, regions, legends and relationships
Images without captions	Image is completely invisible to RAG	Extract image + infer context + optional vision
Caption detached from image	Caption becomes unrelated paragraph	Associate caption spatially
Headers/footers	Pollute every RAG chunk	Detect repeated page elements
Watermarks	"DRAFT" appears 100 times in extraction	Detect repeated/background text
Footnotes	Inserted randomly into main paragraphs	Preserve footnote references and relationships
Hyphenation	govern- ment becomes separate terms	Reconstruct words intelligently
Ligatures	fi, ff, etc. become bad Unicode	Normalize glyphs
Clipped text	Text object exists but isn't actually visible	Compare clipping/render state
Redactions	Hidden underlying text may still be extractable	Detect visual redaction vs underlying content
Annotations	Comments/stamps aren't included	Extract annotations separately
Attachments	Embedded files disappear	Enumerate embedded attachments
Layers/OCGs	Hidden CAD/map layers confuse extraction	Understand visible/hidden layer state
Broken tags	Claims to be accessible but structure is nonsense	Validate tags against actual page content
Fake headings	Large bold text isn't tagged as heading	Infer semantic headings
Incorrect language metadata	Screen readers/OCR use wrong language	Detect probable language
Malformed PDFs	One library refuses to open them	Recovery/repair path
Incremental updates	Old objects remain inside file	Distinguish active revision from stale objects
One of the biggest failures: "searchable" doesn't mean correct

Imagine the page visibly says:

Contract Amount: $2,475,000

but its hidden OCR layer contains:

Contract Arnount: $2475OOO

Most extractors see text and conclude:

✓ Native text available

Then RAG indexes garbage.

CODB Docs should calculate something like:

page.quality = {
  nativeText: 0.42,
  unicode: 0.91,
  readingOrder: 0.76,
  visualAgreement: 0.38,
  ocrRecommended: true
};

Instead of asking only:

if (text.length > 20)

which your current implementation essentially uses as the native-text/OCR decision threshold.

That is something I would change.

Use:

Should OCR?
    │
    ├── no native text
    ├── suspicious Unicode
    ├── abnormal character distribution
    ├── poor word formation
    ├── broken reading order
    ├── text/render disagreement
    ├── missing expected visible regions
    └── extremely low semantic coherence
Another huge one: visible PDF vs internal PDF

I'd make CODB Docs maintain two concepts:

PDF INTERNAL REPRESENTATION
           │
           │ compare
           ▼
RENDERED VISUAL REPRESENTATION

Then flag discrepancies.

For example:

{
  page: 17,

  internal: {
    textObjects: 482,
    images: 3,
    vectors: 912
  },

  visual: {
    textRegions: 31,
    imageRegions: 4,
    tableRegions: 1
  },

  anomalies: [
    {
      type: "hidden_text",
      severity: "warning"
    },
    {
      type: "unrecognized_image",
      bbox: [...]
    }
  ]
}

That starts getting genuinely interesting.

RAG-specific failures are even nastier

A PDF can extract perfectly and still produce terrible RAG.

Consider:

SECTION 4
PROPOSED CONTRACT

Vendor:
ABC Construction

Original Amount:
$1,800,000

Change Order:
$350,000

REVISED CONTRACT VALUE
$2,150,000

A dumb chunker might create:

Chunk 41:
Vendor ABC Construction Original Amount $1,800,000

Chunk 42:
Change Order $350,000 Revised Contract Value

Chunk 43:
$2,150,000

Then ask:

"What's the revised contract amount?"

Embedding retrieval might retrieve Chunk 42 but not Chunk 43 containing the answer.

Your structural system can instead preserve:

SECTION
  │
  ├── Vendor
  │      ABC Construction
  │
  ├── Original Amount
  │      $1,800,000
  │
  ├── Change Order
  │      $350,000
  │
  └── Revised Contract Value
         $2,150,000

Then your retrieval unit isn't merely a text chunk. It's a semantic document object.

That's where CODB Docs can differentiate.

I'd add a PDF "health scan"

Something like:

const report = await doc.diagnose();

returning:

{
  score: 72,

  pages: 186,

  issues: {
    scannedPages: 14,
    brokenTextPages: 3,
    readingOrderProblems: 7,
    duplicateText: 2,
    untaggedTables: 11,
    unrecognizedImages: 23,
    suspiciousOCR: 4,
    accessibilityFailures: 31
  },

  ragReadiness: {
    score: 68,
    searchable: true,
    needsOCR: true,
    needsImageAnalysis: true,
    needsStructureRepair: true
  }
}

And then the rather satisfying:

const repaired =
  await doc.normalize({
    readingOrder: true,
    ocr: "auto",
    deduplicate: true,
    tables: true,
    images: true,
    structure: true
  });
The bigger opportunity

Don't just make CODB Docs answer:

"Can I extract text from this PDF?"

Make it answer:

"Can an AI accurately understand this document?"

Those are radically different questions.

A PDF can be technically valid, searchable, accessible to PDF.js, and still be terrible AI input.

I'd therefore make ragReadiness, extraction confidence, visual/text agreement, structural integrity, image understanding, reading-order confidence, and evidence traceability first-class CODB Docs concepts. That would fit the architecture you're building far better than chasing another generic PDF-to-text extracto
