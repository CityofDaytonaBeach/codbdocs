Yes. I looked specifically at the PDF features that tend to disappear when people reduce a PDF to text + images + vectors, and there is a much bigger opportunity here.

If your goal is:

PDF → one portable JSON representation → JSON → recreate the PDF as closely as possible

then I would not design this as a “PDF vision library.” I'd design it as a PDF document model / intermediate representation (IR) with vision and accessibility layered on top.

The things I'd add that are easy to miss
1. The actual PDF graphics state

This is a huge one.

Don't just store:

{
  "type": "line",
  "x1": 10,
  "y1": 20
}

You need the graphics state at the time the object was painted:

{
  "type": "path",
  "transform": [1, 0, 0, 1, 50, 100],
  "stroke": {
    "color": "#000000",
    "width": 0.5,
    "cap": "round",
    "join": "miter",
    "dash": [3, 2]
  },
  "fill": null,
  "clip": "...",
  "opacity": 0.8,
  "blendMode": "Normal"
}

Otherwise you won't be able to faithfully reconstruct the document.

2. Transforms

This deserves its own first-class representation.

PDF objects aren't necessarily positioned with simple x/y coordinates.

You have:

translation
rotation
scaling
skew
nested transforms
page transforms
image transforms
form XObject transforms

So:

{
  "transform": [a, b, c, d, e, f]
}

should probably be everywhere.

3. Clipping paths

Very easy to overlook.

A PDF can draw a huge object and then clip it to a specific shape.

For example:

Huge image
     ↓
┌─────────────┐
│   CLIP      │
│   ╭─────╮   │
│   │image│   │
│   ╰─────╯   │
└─────────────┘

If your JSON doesn't preserve clipping paths, reconstruction can look completely different.

4. Transparency / blend modes

Not just opacity.

You need things such as:

alpha
soft masks
transparency groups
blend modes
knockout/isolated groups

PDF 2.0 specifically expanded graphics/transparency capabilities.

5. Patterns and shadings

This is another big omission.

PDF fills aren't necessarily:

"fill": "#FF0000"

They can be:

tiling patterns
gradients
axial shadings
radial shadings
mesh shadings

So I'd have:

{
  "paint": {
    "type": "gradient",
    "kind": "radial",
    "stops": [...]
  }
}
6. Fonts need much more than font names

Store:

font identity
embedded font
subset information
encoding
Unicode mapping
glyph IDs
glyph widths
character spacing
word spacing
horizontal/vertical writing
rendering mode
text matrix

This is particularly important because the visible glyph and the extracted Unicode character are not necessarily the same thing. PDF accessibility guidance specifically calls out Unicode mapping and cases where visible graphics/text don't have usable Unicode mappings.

I'd represent text at the glyph level:

{
  "type": "text",
  "glyphs": [
    {
      "gid": 42,
      "unicode": "A",
      "advance": 7.2,
      "transform": [...]
    }
  ]
}

That gives you much better reconstruction.

7. Marked content

This is probably one of the most important things missing from your current model.

PDF can associate page content with the logical structure tree using marked-content sequences.

That relationship is critical for accessibility, reuse, extraction, and semantic understanding.

Your JSON should preserve:

{
  "type": "markedContent",
  "id": "mc_123",
  "tag": "P",
  "properties": {},
  "children": [...]
}

And then separately:

{
  "structure": {
    "type": "P",
    "children": [
      { "ref": "mc_123" }
    ]
  }
}

That separation is important.

8. Artifacts

This is subtle and extremely valuable.

A page number, header, footer, decorative line, etc. might visually exist but not be part of the document's semantic reading order.

PDF accessibility explicitly distinguishes real content from artifacts.

So:

{
  "type": "text",
  "text": "Page 4",
  "role": "artifact",
  "artifactType": "pagination"
}

This lets your system answer:

"Give me the actual content without headers and footers."

9. The structure tree

This should become the semantic backbone of your JSON.

Something like:

{
  "structure": {
    "type": "Document",
    "children": [
      {
        "type": "H1",
        "children": ["Introduction"]
      },
      {
        "type": "P",
        "children": [
          { "ref": "text_31" }
        ]
      },
      {
        "type": "Table",
        "children": [...]
      },
      {
        "type": "Figure",
        "children": [...]
      }
    ]
  }
}

Tagged PDF is specifically intended to represent logical structure, reading order, headings, lists, tables, figures, etc.

10. Structure attributes

Don't stop at tags.

Store attributes such as:

{
  "type": "Table",

    "colSpan": 3,

  }

Also:

language
alternate descriptions
expansion
actual text
table headers
list numbering
pronunciation
MathML-related information

PDF 2.0 expanded the structure/tagging model and added things including namespaces, MathML support and pronunciation hints.

11. Reading order

You want to preserve both:

{

This is crucial for:

footnotes
captions
headers
tables

Logical content order is explicitly part of accessible PDF semantics.

25. Object identity

This is fundamental to your JSON idea.

Don't make your JSON purely hierarchical.

Use IDs:

  "id": "obj_8392",
  "type": "image"
}

and references:

{
  "type": "figure",
  "content": ["obj_8392"]
}

Why?

Because PDFs reuse objects.

For example, one logo can be painted on 100 pages without storing 100 copies.

Your JSON should preserve that relationship.

Same concept.

Represent:

{
  "resources": {
    "xobjects": {
      "logo": {...}
    }
  }
}

and then:

{
  "draw": {
    "xobject": "logo",
    "transform": [...]
  }
}

This makes your JSON much smaller and makes exact reconstruction easier.

Don't just:

}

Instead:

  "id": "img_17",

    "encoding": "jpeg",
    "bytes": "..."
  },

    "transform": [...]
  },

  "content": {
    "ocr": [...],
    "objects": [...],
    "description": "..."
  }

That separates:
