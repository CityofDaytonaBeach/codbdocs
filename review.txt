8. Add query planning

Don't treat every query identically.

"What is the contract amount?"

becomes:

{
  intent: "value_lookup",
  subject: "contract",
  expected: "currency"
}

While:

"Who approved it?"

becomes:

{
  intent: "relationship_lookup",
  relation: "approvedBy",
  expected: "person"
}

And:

"Which project costs the most?"

becomes:

{
  intent: "comparison",
  subject: "project",
  metric: "currency",
  operation: "max"
}

That last one is important.

An embedding doesn't calculate:

MAX(project.cost)

Your engine can.

The API I would target for 1.0

Ultimately, all this machinery should disappear behind:

const doc =
  await CodbDocs.load(file);

await doc.prepare();

const result =
  await doc.query(
    "Who approved the $425,000 contract?"
  );

Return:

{
  answer: "Jane Smith",

  confidence: 0.97,

  sources: [
    {
      page: 17,
      bbox: [...],
      text: "Approved by Jane Smith"
    }
  ],

  reasoning: {
    intent: "relationship_lookup",

    matched: [
      "contract",
      "$425,000",
      "approved by"
    ],

    relationship:
      "contract → approvedBy → person"
  }
}

No model. No GPU. No API. No vector database. No server.

The most important next milestone isn't "more PDF support." It's CODB Docs 1.0 Retrieval Engine: quality scoring → normalized IR → concept graph → relationship graph → fingerprints → hybrid deterministic retrieval → query planner → evidence ranking → citations. Once that loop works exceptionally well and is benchmarked, the rest of the library has something coherent to orbit around instead of becoming a museum of impressive PDF functions.
