Exactly. CODB Docs should be headless. It should build the accessible/intelligent document representation and provide the data and behaviors. The consuming React, Lovable, Vue, or JavaScript app decides entirely what it looks like.

Think:

CODB Docs = engine
User's app = UI

CODB Docs should produce something like:

const access = await graph.createAccessibleView();

const data = access.toJSON();

Returning:

{
  document: {
    title: "City Commission Agenda",
    language: "en"
  },

  outline: [
    {
      id: "financial-impact",
      title: "Financial Impact",
      level: 1,
      page: 17
    }
  ],

  sections: [
    {
      id: "financial-impact",
      heading: "Financial Impact",
      content: [...]
    }
  ],

  tables: [...],
  images: [...],
  links: [...],

  accessibility: {
    score: 96,
    issues: [...]
  }
}

Then the developer decides whether that becomes a DocAccess-looking page, a custom city website, a Lovable component, a mobile interface, or something entirely different.

For example, React could do:

function AccessibleDocument({ access }) {
  return (
    <main>
      <MyNavigation
        items={access.outline}
      />

      <MyDocumentContent
        sections={access.sections}
      />
    </main>
  );
}

Or somebody could make something completely different:

<Tabs>
  <Tab title="Document">
    <AccessibleContent />
  </Tab>

  <Tab title="Original PDF">
    <PDFViewer />
  </Tab>

  <Tab title="Search">
    <Search />
  </Tab>
</Tabs>

CODB Docs shouldn't care.

Even toHTML() should be mostly unstyled

I'd have:

access.toHTML()

generate semantic HTML, not a designed website:

<article>
  <h1>Budget Report</h1>

  <section id="financial-impact">
    <h2>Financial Impact</h2>

    <p>...</p>

    <table>
      <caption>Funding Accounts</caption>
      ...
    </table>
  </section>
</article>

Not this:

<div
  style="
    background:#123456;
    border-radius:20px;
    box-shadow:...
  "
>

Please spare the SDK from becoming an interior decorator.

I would actually provide three output levels

Raw data:

access.toJSON()

Maximum design freedom.

Semantic HTML:

access.toHTML()

Ready to insert into an application and style with CSS.

React primitives/hooks:

const {
  document,
  outline,
  sections,
  search,
  ask,
  navigate
} = useCodbAccessible(graph);

But avoid forcing:

<CodbAccessibleDocument />

as the only route. You could provide a reference component for convenience, but the hooks/data API should be the important product.

That also makes it excellent for Lovable. You could tell Lovable:

Use @codbdocs/react to generate the accessible document model. Design the interface using our existing application components and branding.

Lovable handles appearance while CODB Docs handles the rather less glamorous problem of figuring out what a deranged 417-page PDF actually means.

So yes: add the feature to core as a headless document-building API, not as a predetermined UI. That's the architecture I'd recommend.
